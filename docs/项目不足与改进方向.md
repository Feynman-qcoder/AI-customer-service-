# 项目不足与改进方向

本文只描述当前公开代码可以直接验证的边界，以及适合继续投入的工程方向。建议项不代表已经实现。

## 当前边界

### 部署与扩展

- checkpoint 使用本地 SQLite，设计目标是单主机、单进程、单 worker；横向扩容前需要更换共享状态后端并重新验证并发语义。
- Docker Compose 适合本地演示和功能验证，不包含面向生产环境的集群编排、自动扩缩容、跨可用区容灾与密钥托管。
- 示例账号、商品、订单和知识资料只用于本地体验，不能直接作为生产数据。

### 模型与检索

- Mock 模式用于离线开发，不能代表真实模型的准确性、稳定性、延迟或成本。
- 真实模型的表现会受到服务提供方、提示配置、文档质量和向量模型的共同影响，需要建立独立评测集再作判断。
- 知识库支持解析、切分、检索和引用，但仍需要补充内容审核、版本治理、失效策略和检索质量监控。

### 渠道与人工协同

- 当前主要交互入口是 Web，尚未提供电话、邮件、即时通讯平台等多渠道适配器。
- 系统具备用户确认和管理员审批链路，但坐席队列、服务级别策略、转人工摘要和人工接管体验仍可继续完善。
- 管理界面聚焦审批与基础运营，尚未覆盖完整的客服工作台和团队管理能力。

### 可观测性与运维

- 已提供健康检查、结构化运行记录和脱敏边界，但生产环境仍需要对接统一指标、日志、链路追踪与告警平台。
- 备份、恢复、容量规划、故障演练和数据保留策略需要由部署方根据实际基础设施制定。
- 依赖升级、镜像漏洞扫描、软件物料清单和供应链签名应纳入持续集成流程。

## 改进优先级

1. 建立版本化业务评测集，持续验证回答依据、越权隔离、副作用拦截、恢复能力和延迟预算。
2. 引入共享 checkpoint 与分布式租约，完成多实例并发、故障切换和重复执行防护验证。
3. 建设转人工队列和结构化交接包，明确触发条件、上下文范围、超时处理和审计责任。
4. 补充知识内容审批、灰度发布、回滚、过期提醒和检索缺口发现。
5. 将指标、日志和 trace 接入可自托管的观测平台，并为模型、检索、工具和业务动作设置分层告警。
6. 增加渠道适配层，同时坚持服务端身份、最小权限、确认审批和幂等执行边界。

## 安全与数据治理建议

- 生产环境使用独立密钥管理系统，不在源码、镜像或日志中保存真实凭据。
- 将客户身份、订单信息、聊天记录和上传文档纳入分级、脱敏、留存与删除制度。
- 对模型输出、知识内容和外部工具结果都按不可信输入处理，禁止绕过服务端授权和策略层。
- 为退款、取消订单、库存调整等操作保留确认、审批、幂等键、状态校验和完整审计。
- 上线前执行威胁建模、依赖扫描、权限测试、恢复演练和人工复核。
